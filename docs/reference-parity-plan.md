# Reference Parity Plan: ZenForge vs. deepseek-harness and codex

This document is the gap analysis behind the current upgrade wave. It maps
every capability observed in the two reference harnesses —
[deepseek-harness (DSH)](https://github.com/deepseek-ai/deepseek-harness) and
[codex](https://github.com/openai/codex) — onto ZenForge: what ZenForge already
had, what this wave implemented, and what remains as roadmap with a concrete
adoption sketch. It is a living planning artifact, not an ADR; the design
decisions themselves are recorded in `docs/adr/`.

Method: both references were inventoried capability-by-capability from their
sources (DSH `lib/` TypeScript surface, codex `codex-rs/` Rust workspace), then
each item was classified:

- **Shipped** — implemented in this upgrade wave, with tests.
- **Already had** — ZenForge had an equivalent or stronger mechanism before
  this wave.
- **Roadmap** — deliberately deferred, with a sketch of how it would land in
  the ZenForge architecture and a size estimate (S/M/L).

## Cross-cutting principles

Both references converge on the same engineering principles. ZenForge adopts
all of them; the right column points at concrete evidence.

| Principle | Meaning in the references | ZenForge evidence |
| --- | --- | --- |
| Fail-closed enforcement | Policy violations error out; unknown cases deny | `policy.ReviewCommand` denies non-allowlisted commands; `modelretry.Classify` marks unknown failures non-retryable; event-log write failures stop the run |
| Policy, not prompting | Safety lives in code paths the model cannot talk around | Tool argument validation, workspace roots, snapshot CAS, approval gates — none are prompt-level |
| Capability-boundary authorization | Crossing a boundary needs a human decision, once per boundary | Approval broker + grants store; sandbox escalation always prompts (ADR 0025) |
| Provenance on every record | Events/records carry ids, fingerprints, timestamps | Event payloads carry run/step/tool-call ids; `CompactionRecord` carries summarizer model + usage; attempt chaining via `ReplacesID`/`ReplacementID` |
| Durable marker before side effect | The log records intent before the wait/side effect | `model.retry` is emitted and checkpointed **before** the backoff sleep; approval requests checkpoint before pausing |
| Bounded resources | Every store, buffer, and loop has a cap | Attempt history 64, compaction records 64, instructions budget 32 KiB, spill 50 KiB inline, shell output caps, max steps, tool `MaxCalls` |
| Single owning writer | One component owns each mutation path | Runner owns `RunState`; checkpoint store owns persistence; adapters own provider protocol (ADR 0012) |
| Adapter-owned normalization | Core sees one typed contract | `model.Event`/`model.Message`; `model.HTTPStatusError` with `RetryAfter`; sandbox `Session`/`ExecuteResult` |
| Typed contracts | Errors and payloads are structured, not stringly | `tool.ErrInvalidArguments`, `approval.ErrRequired`, `model.StreamIdleError`, `compaction.ErrNoReduction`, typed events |
| Observability as events | Everything noteworthy is an event | ~40 event types incl. `compaction.*`, `model.retry`, `model.superseded`, `instructions.loaded` |

| A36 | Landlock planner + Linux applier | codex `linux-sandbox/src/landlock.rs` | `sandbox/landlock` splits the ABI-aware access arithmetic from the syscalls: the planner computes `EXECUTE/READ_FILE/READ_DIR` read access (whole filesystem by default, or only the declared read roots when `FullDiskRead` is false), full read-write on the writable roots and on named read-write paths such as `/dev/null` (which is also granted by default, because a sandbox that denies writing to the null device breaks ordinary `cmd >/dev/null` shell use), and a `HandledAccess` mask covering every right the probed ABI supports, since an unhandled right is unrestricted rather than denied. The run-starting tool (ADR 0056): `zenforge mcp-server --allow-run` adds `zenforge_run` — the tool does not exist without the grant, so the operator's flag is the capability list and the protocol's unknown-tool error is the answer to an ungranted call. The tool is advertised without `readOnlyHint`, so a conforming client asks *its* own operator, while the grant protects *this* host; the served run is configured entirely by the operator's flags (workspace, tools, sandbox, hooks, checkpoint store — `mcp-server` now binds the standard option set, which it previously did not) and the caller supplies only the prompt; and the run's own approval-required tool calls follow `--approve`: `always` allows them, `never` refuses by choice, and `prompt` — unusable on a stdio server, where the interactive broker would read the protocol stream — becomes a refusal through an `options.approvalOverride` recording deny broker whose reason names the flag to change. Refused calls are reported to the model (which adapts) and to the caller with the run's answer, because a quietly hobbled run is worse than one that says what it refused; a failed, timed-out, or cancelled run is an `isError` result that still carries the run id (`--run-timeout`, default 15 minutes, bounds one run because the server answers requests in order, and a single run slot keeps an embedding host that drives `Handle` concurrently from overlapping two runs on one agent). Making cancellation real here also fixed a pre-existing defect the timeout path exposed: a JSONL checkpoint save that landed and then reported the context error left the loop's sequence counter behind the store, so the terminal cancellation checkpoint collided and the run reported a sequence conflict instead of the cancellation — the store now completes a durably-pending save (and a recovery of one) under a context that cannot be cancelled, and the loop re-derives its counter from the store after a failed save. Per-server time bounds (ADR 0061): `mcpServers.<name>` gained `startupTimeout` and `toolCallTimeout` as Go duration strings, validated before anything is spawned (unparseable or non-positive is a configuration error naming the key), defaulting to the reference's 30-second handshake and 60-second call budgets when absent. The startup bound is the context that covers `initialize` *and* `tools/list` on that server, so a slow-to-wake server is accommodated without slowing every other server's failure detection, and the tool-call bound travels the existing `tool.TimeoutDeclarer` path unchanged. The whole handshake is the unit: a server is not started until it has listed its tools. Persistent cross-run approval grants (ADR 0062) complete the approval story: a *standing* decision was already offered to brokers (`ScopeRule`) but the adapter's gated requests offered only once/reject options, the durable store pinned a rule grant to the exact argument fingerprint (so "always allow" only replayed for byte-identical calls), and the CLI configured no grant store at all. Now a gated remote call offers "Always allow this tool", a rule grant stores the rule key with no fingerprint — `Grant.Scope` plus `EffectiveScope` make the two shapes explicit, and an old store keeps its meaning — the agent looks the rule entry up before the pinned one, and the CLI's `approval.grantsFile` (with optional `grantTtl`, `tenant`, `subject`) opens a durable sqlite store in the namespace its grants belong to, defaulting to `cli` plus the operating-system user and refusing a TTL or namespace that no file could hold. A once- or run-scoped decision still never outlives its run. Listing and revoking are now `zenforge grants list|revoke` (ADR 0063): `approval.GrantLister` is the optional half of a store, both shipped stores enumerate a namespace's live grants in rule-key order with the scope normalized on read, a bare rule key revokes the standing grant while `--fingerprint` selects a payload-pinned entry, `--all` walks the listing, and the file and namespace resolve exactly as the agent resolves them. Detached served runs (ADR 0067): `zenforge_run` accepts `detach: true` and answers with the run id as soon as the run has started, instead of holding the call for the answer; the run is bound to the server's context rather than the call's (so it outlives the request that asked for it) and still to the operator's `--run-timeout`, one run slot at a time, and the server cancels and waits for them on the way out. `zenforge_run_status` (read-only, always advertised, no grant needed) reports a run by id: the live or terminal state of a run this server started, with its answer or its explanation, or the durable checkpoint summary of a run this install recorded, or `unknown` — a fact rather than a handler error — when the id is in neither. The registry is in-process and bounded (100 terminal records, oldest evicted first, a live run never forgotten), and a blocking run is registered too, so any run this server owns is visible while it runs. `zenforge_run_cancel` (ADR 0068, advertised only with the same `--allow-run` grant and without a read-only hint) stops a run this server is still running: cancellation is asynchronous, so the tool waits a bounded two seconds for the run to settle and answers `cancelled` or `cancelling` with `cancelled: true`; a run that already finished answers `alreadyFinished: true` with its status, another process's run answers `recorded` and uncancellable, and only bad usage is an error. `resources` and `prompts` (ADR 0071): `ServerConfig` declares `ServerResource`/`ServerPrompt` beside the tools, `resources/list`, `resources/read`, `prompts/list` and `prompts/get` are served, `initialize` advertises a capability only when something is behind it, an unknown resource URI is the spec's -32002 and an unknown prompt or missing required argument is -32602, a `{name}` URI segment is a template so one `zenforge://runs/{runId}` serves every recorded run, and a panicking resource or prompt handler fails that call without killing the stream. The CLI server exposes `zenforge://runs` and `zenforge://runs/{runId}` (the same summaries `zenforge_runs` reports) and one prompt per workspace command, rendered as inert text with inline shell disabled, its arguments taken from the command's own hint placeholders. Progress and list-changed notifications (ADR 0073): a handler calls `mcp.ProgressFrom(ctx)` and the server writes `notifications/progress` inline for a request that carried `params._meta.progressToken` (echoed verbatim as `json.RawMessage`, non-finite values dropped), before that request's response — a notification is one-way, so it needs no write path off the reader goroutine, which is exactly why server-initiated requests remain unported. `ServerConfig.DynamicLists` opts into advertising `listChanged: true` and enables `NotifyToolsChanged`/`NotifyResourcesChanged`/`NotifyPromptsChanged`; without it the capability stays false and a Notify call errors instead of sending a notification the client was told not to expect, and the CLI server keeps it false because its sets are fixed by its flags. `zenforge_run` reports the run's own events as progress through the same loop that produces its result (`Task.OnEvent`), and a detached run gets a no-op reporter. Server-initiated requests and elicitation (ADR 0074): `Server.Request(ctx, method, params, result)` mints ids in a `srv-` namespace, `Serve` keeps reading while a handler waits (a response frame is routed to its waiter, other frames go to their own handler goroutines), an unknown or late response is dropped rather than treated as an error, every request needs a caller deadline, and a `Serve` return fails pending requests with `ErrStreamClosed`, waits for in-flight handlers so none of their responses is lost, and only then detaches the stream. `Elicit` sends `elicitation/create` with `{message, requestedSchema}` and decodes accept|decline|cancel, refusing with a clear error when the client never advertised the capability or there is no stream -- no server capability is advertised for it, because elicitation is a client capability. Responses are no longer in request order when handlers run concurrently; MCP pairs them by id. Elicitation in the approval path (ADR 0075): with `--approve prompt`, an approval gate asks the MCP client for a boolean decision when it advertised elicitation, granting that one call on `approve: true`, denying it with the reason that the client declined on `approve: false`/decline/cancel, and denying (never consenting) on a non-boolean answer; when the client cannot answer -- not advertised, no stream, timeout, stream ended, RPC error -- the run falls back to the byte-for-byte previous refusal, so a client that cannot answer is exactly where it was. `--approve always`/`never` install no elicitation, and `--allow-run` did not change: answering the question is the client's capability, not a second grant. The server travels with the run, so a detached run can elicit, bounded by the elicitation timeout. `resources/templates/list` and subscriptions (ADR 0076): the template listing returns exactly the `{name}` registrations (no pagination; the set is fixed at startup), and `ServerConfig.ResourceSubscriptions` opts into advertising `resources.subscribe: true` and serving `resources/subscribe`/`resources/unsubscribe` -- without it the method is method-not-found because the capability block is the method list. A subscription may be a concrete URI or a concrete URI matching a watched template, `Server.NotifyResourceUpdated(uri)` delivers `notifications/resources/updated` to subscribers (a template watcher hears about every matching run; an unregistered URI is refused rather than dropped; no subscribers is a silent success; after the stream ends it is `ErrNotServing`), unsubscribe is idempotent, and subscriptions are cleared when `Serve` returns so they never cross connections. The CLI server keeps `subscribe: false` because its resources are recomputed per read and it has no update source. Sampling (ADR 0077): `initialize` records the client's `sampling` capability and `Server.Sample(ctx, SamplingRequest)` asks it for a completion through the existing request channel (`sampling/createMessage`, caller deadline or a documented default, `ErrSamplingUnsupported` when the client never advertised it or there is no stream -- never a hang). `mcp-server --allow-run --sampling` makes served runs use `adapters/mcpsampling`, a `model.Model` that delegates each generation to the client, so the server needs no local credential; a client that cannot sample fails the run with an actionable error rather than falling back to a model the operator did not choose, and the flag is a usage error without `--allow-run`. `sampling/createMessage` has no tool field, so a sampled run reasons in text: tool specs are dropped and a request that requires a tool call is refused loudly, while approvals, events, checkpoints, timeouts, detaching and cancelling are unchanged.
